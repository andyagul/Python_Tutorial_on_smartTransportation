# 第一部分　知识讲解

## 9.1 场景导入：一条坏数据不该毁掉整批统计

路侧传感器会掉线、司机会误输入、文件可能被删除、除数为零随时发生。没有异常处理的程序，一条坏数据就能让整批统计中断；有异常处理的程序，能"跳过坏数据、记录问题、继续跑完"。

关键心态转变：**异常不是"错误"，而是"一种可预期的运行状态"**。`int("abc")` 抛 `ValueError` 是 Python 在正常汇报"这段文字转不成数字"，处理掉即可，不必视为程序缺陷。

## 9.2 知识点 9.1　异常概念与六种常见类型

### 9.2.1 核心概念

异常是程序运行期间的"意外中断信号"。它带有**类型**与**信息**，`Traceback` 会指出文件、行号与调用链。

本章涉及的六种类型，几乎覆盖交通数据处理中的全部真实情况：

| 异常类型 | 触发条件 | 交通场景示例 |
|---|---|---|
| `ValueError` | 类型对但值不合法 | `int("abc")`、`int("")`、`float("快")` |
| `TypeError` | 类型不匹配 | `"周期：" + 130` |
| `ZeroDivisionError` | 除数为 0 | 长度为 0 时算密度 |
| `FileNotFoundError` | 文件不存在 | 读被删除的日志 |
| `IndexError` | 下标越界 | 字段不足时访问 `parts[2]` |
| `KeyError` | 字典键不存在 | `ledger["京X99999"]` |

**原理补充（概念深化）**：Python 把异常实现为类，所有内置异常都继承自 `BaseException`，日常捕获的 `ValueError`、`IndexError` 等又继承自 `Exception`。`except 类型` 的匹配本质是按 `isinstance` 的子类关系自外向内比对，所以把父类写在前面会吞掉后面的子类分支，这是 `except Exception` 必须垫底的原因。异常抛出后解释器做栈展开：沿调用链逐层回退，寻找能匹配的处理块，一找到就停止；若一路没人接，最外层解释器打印 `Traceback` 并以非零码退出。对空字段调用 `int` 抛 `ValueError` 而非 `TypeError`，是因为参数类型合法、只是值无法解析——类型检查发生在转换逻辑之前。理解「异常是一个带类型与信息的对象」而非「一段报错文字」，才能明白为何能用 `as e` 把它接住、读取 `str(e)` 并写进日志，而 `AttributeError`、`NameError` 这类编码缺陷不该靠捕获掩盖。

### 9.2.2 语法要点

- 异常类型名可直接写在 `except` 后，**不加引号、不加括号**；
- `int("")` 抛的是 `ValueError`（不是 `TypeError`），这是 CSV 空字段处理的要点；
- `AttributeError`、`NameError`、`SyntaxError` 也常见，但多属编码错误，不应靠 `except` 掩盖。

### 9.2.3 常见用法与易错点

| 易错点 | 现象 | 修正 |
|---|---|---|
| 把 `except` 写成 `except ValueError, e` | 语法错误（Python 2 写法） | `except ValueError as e:` |
| 捕获 `Exception` 一把抓 | 掩盖真实缺陷，难排查 | 先捕获具体类型 |
| 空 `except: pass` | 问题被吞掉，数据静默丢失 | 至少打印或计数 |
| 认为 `IndexError` 与 `KeyError` 可互换 | 列表用 `IndexError`、字典用 `KeyError` | 按容器选类型 |

### 9.2.4 随堂示例：四类常见异常分别是什么样

**核心要点**：逐个触发 `ValueError` / `ZeroDivisionError` / `IndexError` / `KeyError`，用 `as e` 打印异常自带的说明，建立「按类型捕获」的直觉。

```python demo9-1
try:
    int("abc")                     # 字符串转不成数字
except ValueError as e:
    print("ValueError：", e)

try:
    1 / 0                          # 除数为零
except ZeroDivisionError as e:
    print("ZeroDivisionError：", e)

try:
    [1, 2][5]                      # 下标越界
except IndexError as e:
    print("IndexError：", e)

try:
    {"a": 1}["b"]                  # 键不存在
except KeyError as e:
    print("KeyError：", e)
```

**预期输出**：

```text
ValueError： invalid literal for int() with base 10: 'abc'
ZeroDivisionError： division by zero
IndexError： list index out of range
KeyError： 'b'
```

**变式代码（迁移练习）**：把 demo9-1 的四条独立 try 逐个触发收进一个解析函数与一条循环，对一批卡口日志逐条分类，验证异常类型可用 `type(e).__name__` 区分、且单条失败不会中断整批。

```python demo9-1b
# 卡口日志 时间|车牌|车速：把逐个触发改为逐条分类诊断
def parse(line):
    try:
        speed = int(line.split("|")[2])     # 缺字段抛 IndexError，空字段抛 ValueError
        return "录入 " + str(speed) + " km/h"
    except (IndexError, ValueError) as e:
        return type(e).__name__ + "：" + str(e)
for line in ["08:15|京A|62", "08:16|京B", "08:17|津C|", "08:18|冀D|78"]:
    print(line, "->", parse(line))
print("四条均返回结果，异常未逃逸、程序未中断")
```

**预期输出**：

```text
08:15|京A|62 -> 录入 62 km/h
08:16|京B -> IndexError：list index out of range
08:17|津C| -> ValueError：invalid literal for int() with base 10: ''
08:18|冀D|78 -> 录入 78 km/h
四条均返回结果，异常未逃逸、程序未中断
```

### 9.2.5 实操步骤（上机跟随）

1. 运行代码，核对首行 `08:15|京A|62 -> 录入 62 km/h`，说明该条日志三个字段齐全、转换成功。
2. 核对第二条 `08:16|京B` 的输出以 `IndexError` 开头，因为切分后只有两个字段、取下标 2 越界。
3. 核对第三条 `08:17|津C|` 的输出以 `ValueError` 开头且信息里带空串标记，验证空字段触发的是值错误而非类型错误。
4. 核对第四条 `08:18|冀D|78 -> 录入 78 km/h`，说明坏数据之后的好数据仍被处理、循环未中断。
5. 把 `except (IndexError, ValueError)` 改成只留 `ValueError` 重跑，`08:16|京B` 的 `IndexError` 将逃逸并导致非零退出码，体会按类型列全的必要性。

### 9.2.6 常见问题 FAQ

| 现象 | 根因 | 处理 |
|---|---|---|
| 对空串调用 `int` 却想靠 `TypeError` 兜住，异常仍逃逸 | 空串类型合法、只是值无法解析，抛的是 `ValueError` | 改捕获 `ValueError`；类型不匹配才用 `TypeError` |
| 列表取 `parts[2]` 越界却写了 `except KeyError` | `IndexError` 归序列下标、`KeyError` 归字典键，二者不互换 | 列表用 `IndexError`、字典用 `KeyError`，按容器选类型 |
| 写了 `except Exception` 后具体分支不再执行 | 父类按子类关系先匹配，会吞掉后面的具体类型 | 具体类型在前、`Exception` 垫底，避免一把抓 |


## 9.3 知识点 9.2　`try` / `except` / `else` / `finally`

### 9.3.1 核心概念

```text
try:
    可能出错的语句
except 异常类型A:
    处理 A
except 异常类型B:
    处理 B
else:
    try 内无异常时执行
finally:
    无论是否异常都执行
```

四个子句的执行时机是本知识点最容易被考到的内容：

| 子句 | 何时执行 | 典型用途 |
|---|---|---|
| `try` | 始终 | 放"可能出错"的语句，范围尽量小 |
| `except` | 对应类型异常被抛出时 | 给出可读提示、记录日志、继续流程 |
| `else` | `try` 内**没有**异常时 | 放"成功后"的处理，与 `try` 分离 |
| `finally` | **无论是否异常** | 收尾：关闭资源、打印分隔、写审计日志 |

**原理补充（概念深化）**：`try` 并非把代码包起来就安全：解释器为它维护一张异常处理表，一旦块内抛错就跳到表中登记的第一个匹配 `except`；`else` 只在无异常时执行，是因为它被编译成正常路径尾部的续接块，异常路径会直接绕过它。`finally` 最特殊，编译器会把它的代码复制到正常、异常、`return`、`break` 等每一条出口之前，因此无论中途是否返回、是否抛错都必然执行——这正是收尾用 `finally`、成功逻辑用 `else` 的底层原因。一个常见误解是以为 `return` 能跳过 `finally`：实际返回值会先被暂存，`finally` 执行完才真正交还调用者；若 `finally` 里自己写了 `return`，还会覆盖暂存值。把 `try` 范围收小，本质是让异常表更精确，出错时 `Traceback` 才能指到真正的语句，而不是笼统地指向整个程序。

### 9.3.2 语法要点

- 多个 `except` 按**从具体到宽泛**排列，先写 `ValueError` 再写 `Exception`；
- `else` 与 `finally` 均可省略，但 `try` 至少配一个 `except` 或 `finally`；
- `try` 范围越小越好：把整个程序包进 `try` 会导致"出错也看不出在哪"。

### 9.3.3 常见用法与易错点

| 易错点 | 现象 | 修正 |
|---|---|---|
| `except` 顺序写反 | 具体分支永不执行 | 具体在前、宽泛在后 |
| 把成功逻辑写在 `try` 内 | 成功路径与出错路径混在一起 | 成功逻辑移到 `else` |
| 用 `else` 代替 `finally` | 异常时收尾未执行 | 收尾用 `finally` |
| 混淆 `else` 的两种含义 | 与 `for-else`（未被 `break` 才执行）混为一谈 | 记住 `try-else` 是"无异常才执行" |

### 9.3.4 随堂示例：try / except / else / finally 的执行次序

**核心要点**：验证四个子句的分工：`try` 放可能出错的代码、`except` 只在出错时执行、`else` 只在**没出错**时执行、`finally` 无论成败都执行。

```python demo9-2
def divide(a, b):
    try:
        result = a / b
    except ZeroDivisionError:
        print("[出错] 除数不能为 0")
        return None
    else:
        print("[成功] 结果 =", result)
        return result
    finally:
        print("—— 本次计算结束 ——")

divide(10, 4)
print()
divide(10, 0)
```

**预期输出**：

```text
[成功] 结果 = 2.5
—— 本次计算结束 ——

[出错] 除数不能为 0
—— 本次计算结束 ——
```

**变式代码（迁移练习）**：把 demo9-2 的两次调用看打印改为用列表 `seq` 记录子句命中顺序，验证正常只走 `else`、异常只走 `except`、两种情况都追加 `finally`。

```python demo9-2b
# 记录四个子句的执行时机：正常走 else，异常走 except，两者都走 finally
seq = []
def calc(a, b):
    try:
        r = a / b
    except ZeroDivisionError: seq.append("except")
    else: seq.append("else")
    finally: seq.append("finally")
    return 0 if b == 0 else round(r, 1)
print("结果：", calc(96, 2.5), calc(96, 0), "| 子句序列：", seq)
```

**预期输出**：

```text
结果： 38.4 0 | 子句序列： ['else', 'finally', 'except', 'finally']
```

### 9.3.5 实操步骤（上机跟随）

1. 运行后核对结果一行为 `38.4 0`：96/2.5 保留一位是 38.4，除零那次按 `b == 0` 返回 0。
2. 核对子句序列为 `['else', 'finally', 'except', 'finally']`，第一次调用命中 `else`、第二次命中 `except`。
3. 数出 `finally` 共出现 2 次，与调用次数相等，验证它无论成功失败都执行。
4. 把 `96 / 0` 换成 `96 / 2` 重跑，序列会变成两次 `['else', 'finally']`，`except` 一次也不出现。
5. 把 `return 0 if b == 0 else round(r, 1)` 改成无条件 `round(r, 1)`，除零那次会因 `r` 未赋值抛 `NameError`，反证条件表达式的惰性求值保护了异常分支。

### 9.3.6 常见问题 FAQ

| 现象 | 根因 | 处理 |
|---|---|---|
| 把成功后的输出写进 `try`，出错路径也跟着执行 | 成功逻辑与监控代码混在一起，异常时行为难控 | 把成功逻辑移到 `else`，`try` 只放可能出错的语句 |
| 用 `else` 代替 `finally` 做收尾，异常时收尾没执行 | `else` 只在无异常时执行，异常路径会绕过它 | 收尾一律放 `finally`，它才保证始终执行 |
| 把 `try-else` 当成 `for-else` 理解 | 两者的否则含义不同：`for-else` 是未被 `break` 才执行 | 记住 `try-else` 是 `try` 内无异常才执行 |


## 9.4 知识点 9.3　`except ... as e` 与多异常捕获

### 9.4.1 核心概念

`except 类型 as e:` 把异常对象绑定到 `e`，可读取其信息（`print(e)`）用于日志。多异常捕获有两种写法：

| 写法 | 含义 | 适用 |
|---|---|---|
| `except (ValueError, IndexError) as e:` | 两种异常同一处理 | 处理方式相同 |
| 分开写两个 `except` | 分别处理 | 需要不同提示语 |

**原理补充（概念深化）**：`except 类型 as e` 里的 `e` 只在 `except` 块内有效：Python 3 在块结束时会主动 `del e`，目的是断开异常对象到回溯对象、再到栈帧与局部变量的引用环，让内存及时回收，否则 `Traceback` 会一直拽着整条调用栈不放。因此想把诊断留到后面，应存 `str(e)` 或 `type(e).__name__` 这样的值，而不是保存 `e` 本身。`except (A, B) as e` 的括号不是列表而是异常元组，解释器逐个做类型匹配；写成 `except A, B:` 在 Python 3 会被当作旧语法而报错。另一层误解是捕获即消失：不写 `raise` 时异常确实被消化、流程继续，但它携带的栈信息也随之丢弃，所以关键日志应在 `except` 内当场记录，而不是等块外再补。

### 9.4.2 语法要点

- `e` 的作用域只在 `except` 块内；
- `str(e)` 给出异常的描述信息（如 `invalid literal for int() with base 10: 'abc'`），可直接写入日志；
- 捕获后**不写 `raise`** 即为"吞掉异常"，流程继续；写 `raise` 则向上传递。

### 9.4.3 常见用法与易错点

| 易错点 | 现象 | 修正 |
|---|---|---|
| 元组漏括号 | `except ValueError, IndexError:` 语法错误 | 加圆括号 |
| 只捕获一种 | 另一种异常仍中断程序 | 按实际情况列全 |
| `as e` 后未使用 | 提示信息不足，难定位 | 打印或写入日志 |

### 9.4.4 随堂示例：一个 except 捕获多种异常

**核心要点**：验证 `except (A, B) as e` 的写法可同时捕获多类异常，并用 `type(e).__name__` 区分实际发生的类型；`else` 用于「没出错时」的正常处理。

```python demo9-3
def parse(item):
    try:
        speed = int(item)
        if speed > 300:
            raise ValueError("车速超出 0~300")
    except (ValueError, TypeError) as e:
        print("跳过", item, "→", type(e).__name__, ":", e)
        return None
    else:
        print("录入成功：", speed)
        return speed

for v in ["62", "abc", "999"]:
    parse(v)
```

**预期输出**：

```text
录入成功： 62
跳过 abc → ValueError : invalid literal for int() with base 10: 'abc'
跳过 999 → ValueError : 车速超出 0~300
```

**变式代码（迁移练习）**：把 demo9-3 的元组合并捕获改为两条 `except` 按类型分别给不同诊断语，验证 `as e` 取出的信息可用于分类提示、两类异常各走各的分支。

```python demo9-3b
# 同样的坏数据改用两个 except 分别处理，验证按类型给不同提示语
def parse(rec):
    try:
        return "通过 " + str(int(rec.split("|")[1]))
    except IndexError:
        return "字段不足：缺少车速列"
    except ValueError as e:
        return "车速非数字：" + str(e)
for rec in ["京A|62", "京B|快", "京C", "冀D|78"]:
    print(rec, "->", parse(rec))
```

**预期输出**：

```text
京A|62 -> 通过 62
京B|快 -> 车速非数字：invalid literal for int() with base 10: '快'
京C -> 字段不足：缺少车速列
冀D|78 -> 通过 78
```

### 9.4.5 实操步骤（上机跟随）

1. 运行代码，核对 `京A|62 -> 通过 62`，说明两段字段且车速为整数时走成功返回。
2. 核对 `京B|快` 输出以车速非数字开头，命中 `except ValueError as e`，`str(e)` 里含 `invalid literal`。
3. 核对 `京C` 输出为字段不足：缺少车速列，命中前面的 `except IndexError`，证明两条分支按类型分流。
4. 核对 `冀D|78 -> 通过 78`，坏数据之后流程继续，未因异常中断。
5. 把两个 `except` 合并成 `except (IndexError, ValueError):` 重跑，两类坏数据会共用同一句提示，验证分开写才能给不同诊断语。

### 9.4.6 常见问题 FAQ

| 现象 | 根因 | 处理 |
|---|---|---|
| `except ValueError, IndexError:` 报语法错 | 元组漏了圆括号，Python 3 不再支持 Python 2 的逗号写法 | 写成 `except (ValueError, IndexError) as e:` |
| 只捕获一种异常，另一种一来程序就中断 | 未列出的异常类型没有匹配分支，继续向上抛出 | 按实际可能列出全部预期类型 |
| `as e` 接了却没用，日志只有笼统一句 | 未读取 `e` 的信息，丢失了具体诊断文本 | 打印 `type(e).__name__` 与 `str(e)` 写进日志 |


## 9.5 知识点 9.4　`raise` 与 `assert`

### 9.5.1 核心概念

前两个知识点是"接住别人抛的异常"，本知识点是"自己抛出异常"：

| 工具 | 写法 | 用途 | 抛出类型 |
|---|---|---|---|
| `raise` | `raise ValueError("车速不能为负")` | 业务规则校验 | 指定类型 |
| `assert` | `assert len(plate) == 7, "长度错误"` | 内部不变量（调试、入口参数） | `AssertionError` |

`assert 条件, "提示"` 等价于 `if not 条件: raise AssertionError("提示")`，但**在 `python -O` 优化模式下会被移除**，因此生产环境的强制校验必须用 `if + raise`。

**原理补充（概念深化）**：`assert 条件, 提示` 在字节码层面大致等价于条件不成立时 `raise AssertionError(提示)`，但关键差别是它受 `__debug__` 开关控制：以 `python -O` 运行时编译器会整段丢弃 `assert`，连条件都不求值。所以断言适合表达代码内部必然成立的前提（如入口参数类型），绝不能用来挡文件、网络、用户输入带来的脏数据——生产校验必须写成 `if + raise ValueError(...)`，它是不可被优化掉的普通控制流。`raise` 后既可跟异常类（解释器自动实例化）也可跟实例；一旦执行，当前块后续语句全部不可达，控制流立刻转入栈展开。讲义强调的内层抛、外层接，本质是把发现问题与决定处置解耦：校验函数只管抛，调用方才决定拒绝、跳过还是记日志，同一套校验因此能被不同流程复用。

### 9.5.2 语法要点

- `raise` 的提示语应让运维人员**直接定位问题**："车速超出合理范围 0~300：320"优于"数据错误"。
- 函数内部校验失败时，常见两种策略：**抛异常**（让调用方决定如何处理）或**返回 `False` / `None`**（自身消化）。案例 9-2 采用"内层抛、外层接"的分层策略。
- `raise` 后可跟异常类（自动实例化）或异常实例。

### 9.5.3 常见用法与易错点

| 易错点 | 现象 | 修正 |
|---|---|---|
| 用 `assert` 做用户输入校验 | `-O` 模式下校验消失 | 用 `if + raise` |
| 抛出 `Exception` | 过于宽泛，调用方无法精确捕获 | 用具体类型 |
| 提示语无信息量 | 排查困难 | 带上具体值与期望范围 |
| `raise` 后继续写代码 | 该段永不执行 | 删除或移到 `else` |

### 9.5.4 随堂示例：assert 断言与 raise 主动抛出

**核心要点**：验证两者差别：`assert` 用于「必须成立的前提」，失败抛 `AssertionError`；`raise` 用于「业务规则不允许的情况」，可指定异常类型与提示。

```python demo9-4
def check_speed(speed):
    assert isinstance(speed, (int, float)), "车速必须是数字"
    if speed < 0 or speed > 300:
        raise ValueError("车速超出 0~300：" + str(speed))
    return "通过"

for v in [62, 320, "快"]:
    try:
        print(v, "→", check_speed(v))
    except AssertionError as e:
        print(v, "→ 断言失败：", e)
    except ValueError as e:
        print(v, "→ 数值非法：", e)
```

**预期输出**：

```text
62 → 通过
320 → 数值非法： 车速超出 0~300：320
快 → 断言失败： 车速必须是数字
```

**变式代码（迁移练习）**：把 demo9-4 的单函数内 try 加多分支拆成内层 check 只抛、外层循环里的 try 按类型接的分层结构，验证 `assert` 抛 `AssertionError`、`raise` 抛指定类型且都不逃逸。

```python demo9-4b
# 分层校验：内层 assert 守类型、raise 守范围，外层按类型分别接住
def check(v):
    assert isinstance(v, int), "车速必须是整数"
    if v < 0 or v > 300: raise ValueError("车速越界：" + str(v))
    return "通过 " + str(v)
for v in [62, 320, "快"]:
    try: print(v, "->", check(v))
    except AssertionError as e: print(v, "-> AssertionError：", e)
    except ValueError as e: print(v, "-> ValueError：", e)
```

**预期输出**：

```text
62 -> 通过 62
320 -> ValueError： 车速越界：320
快 -> AssertionError： 车速必须是整数
```

### 9.5.5 实操步骤（上机跟随）

1. 运行代码，核对 `62 -> 通过 62`，说明 `assert` 与 `raise` 两条防线都未触发。
2. 核对 `320` 走 `ValueError` 分支并带车速越界：320，是 `if + raise` 主动抛出后被循环内的 `except` 接住。
3. 核对 `快` 走 `AssertionError` 分支、提示车速必须是整数，抛出类型与上一行不同。
4. 核对三行输入都打印了结果、没有 `Traceback`，说明内层 `check` 抛出的异常都在外层被消化、循环未中断。
5. 把 `assert` 那行改成类型不符时 `raise TypeError` 并重跑，`快` 会改走 `TypeError` 分支，体会断言与主动抛出在类型及 `-O` 下的差别。

### 9.5.6 常见问题 FAQ

| 现象 | 根因 | 处理 |
|---|---|---|
| 用 `assert` 挡用户输入，加了 `-O` 后校验消失 | `assert` 受 `__debug__` 控制，优化模式下被整段丢弃 | 生产校验用 `if + raise ValueError(...)`，不用断言 |
| 抛 `Exception` 且提示语笼统，调用方无法精确捕获 | 抛出类型过于宽泛，调用方只能一把抓 | 抛具体类型并带上具体值与期望范围 |
| `raise` 后面还写了赋值语句却从不生效 | `raise` 立刻转入栈展开，同一块后续语句不可达 | 把代码删掉或移到 `else` 与函数外 |


## 9.6 知识点 9.5　容错模式：跳过坏数据、继续处理

### 9.6.1 核心概念

批处理的核心要求是"**单条失败不影响整批**"。标准骨架：

```text
for 每条数据:
    try:
        解析 + 校验
    except 具体异常 as e:
        记录原因
        continue          # 跳过本条
    正常处理
```

三个要素：**循环在外、`try` 在内、`continue` 跳过**。若把 `try` 包住整个循环，第一条坏数据就会终止整批。

**原理补充（概念深化）**：容错模式的要害不在 `except` 怎么写，而在 `try` 放在循环的哪一层。若把整个 `for` 包进一个 `try`，任何一条坏数据抛错都会跳出整个循环，后续数据全部丢失，正是一条坏数据毁掉整批的由来；正确骨架是循环在外、`try` 在内，让每条数据拥有独立的异常处理表。`continue` 必须放在 `except` 末尾，否则坏数据会掉进后面的 `append` 或求和语句，甚至因变量未重新赋值而沿用上一轮旧值，酿成比崩溃更隐蔽的统计污染。内存视角看，`valid` 列表只累积成功解析出的对象，失败项从未进入，故 `len(raw) - len(valid)` 天然等于失败条数。最后一个易错点是零有效数据：算平均值前先判断 `len(valid)`，用条件表达式兜底，避免分母为 0 触发 `ZeroDivisionError`，这与前面章节先判断再计算一脉相承。

### 9.6.2 语法要点

- `continue` 放在 `except` 末尾，确保坏数据不进入后续统计；
- 需要统计"成功/失败条数"时，用两个计数器在 `try` 成功路径与 `except` 中分别累加；
- 处理结果用 `(值, None)` / `(None, 错误)` 这类约定返回，便于调用方判断——这是第 8 章"返回 `None` 表示缺数据"的延续。

### 9.6.3 常见用法与易错点

| 易错点 | 现象 | 修正 |
|---|---|---|
| `try` 包住整个循环 | 一条坏数据终止全部 | `try` 移到循环内 |
| `except` 后忘记 `continue` | 坏数据继续参与统计 | 加 `continue` |
| 只用 `print` 不计数 | 无法给出"处理了多少条" | 加计数器 |
| 捕获过宽 | 逻辑错误被当成数据错误吞掉 | 只捕获预期类型 |

---

### 9.6.4 随堂示例：坏数据跳过、好数据继续

**核心要点**：验证容错模式的标准骨架：`try` 内解析、`except` 内记录原因并用 `continue` 跳过，循环不中断，最终只汇总有效数据。

```python demo9-5
raw = ["62", "abc", "-5", "118"]

valid = []
for item in raw:
    try:
        speed = int(item)
        if speed < 0:
            raise ValueError("车速不能为负数")
    except ValueError as e:
        print("[跳过]", item, "原因：", e)
        continue                    # 跳过本条，继续下一条
    valid.append(speed)

print("有效数据：", valid)
print("有效", len(valid), "条，无效", len(raw) - len(valid), "条")
print("有效平均车速：", round(sum(valid) / len(valid), 1), "km/h")
```

**预期输出**：

```text
[跳过] abc 原因： invalid literal for int() with base 10: 'abc'
[跳过] -5 原因： 车速不能为负数
有效数据： [62, 118]
有效 2 条，无效 2 条
有效平均车速： 90.0 km/h
```

**变式代码（迁移练习）**：把 demo9-5 的 raise 判负加打印跳过原因改为靠 `int()` 自然抛错、`valid` 列表配合 `len` 统计成败，并加条件表达式兜底，验证零有效数据不触发除零。

```python demo9-5b
# 容错骨架：坏数据 continue 跳过，好数据进列表；空集用条件表达式兜底防除零
raw = ["62", "abc", "118", "快"]
valid = []
for item in raw:
    try: valid.append(int(item))       # 非数字抛 ValueError 并跳过
    except ValueError: continue        # 坏数据不进入统计
print("有效", valid, "共", len(valid), "条，无效", len(raw) - len(valid), "条")
print("平均车速：", round(sum(valid) / len(valid), 1) if valid else "无有效数据")
```

**预期输出**：

```text
有效 [62, 118] 共 2 条，无效 2 条
平均车速： 90.0
```

### 9.6.5 实操步骤（上机跟随）

1. 运行代码，核对首行有效 [62, 118] 共 2 条、无效 2 条，`abc` 与 `快` 因 `int()` 抛 `ValueError` 被跳过。
2. 核对第二行平均车速： 90.0，即 `(62+118)/2`，被跳过的数据没有进入分子分母。
3. 把 `except ValueError: continue` 里的 `continue` 删掉重跑，`valid` 会沿用上一轮旧值而被污染，观察统计如何失真。
4. 把 `raw` 全部换成非法字符串（如 `abc`、`快`、空串）重跑，核对走兜底分支打印无有效数据，验证零有效数据不抛 `ZeroDivisionError`。
5. 把 `try` 缩进移到 `for` 外面重跑，第一条坏数据就会终止整批，验证 `try` 必须在循环内。

### 9.6.6 常见问题 FAQ

| 现象 | 根因 | 处理 |
|---|---|---|
| 第一条坏数据就终止了整批处理 | `try` 包住了整个 `for`，异常跳出循环 | 把 `try` 移到循环内，让每条数据独立处理 |
| `except` 后忘写 `continue`，坏数据混进了统计 | 坏数据掉进后续 `append` 与求和，甚至沿用上一轮旧值 | 在 `except` 末尾加 `continue` 跳过本条 |
| 全部数据非法时算平均值报 `ZeroDivisionError` | `len(valid)` 为 0 时做了除法 | 先判断有效条数，用条件表达式兜底 |

## 案例 9-1　交通参数录入的容错处理

```python case1_录入容错.py
# ---------- 第 09 章 异常处理 · 案例 9-1：交通参数录入的容错处理 ----------

# 功能说明：用同一段代码演练三种情形：正常录入、路段长度为 0、车道数输入非数字

finally:
    print("=== 本次录入结束 ===")
```

## 案例 9-2　用 raise 与 assert 做数据校验

- **覆盖知识点**：9.4（`raise` / `assert`）、9.3（`except ... as e`）、9.2（`finally`）、第 6 章（函数分层）

1. 用 `assert` 校验车牌长度（断言失败抛 `AssertionError`）；
2. 用 `raise ValueError(...)` 抛出自定义提示的业务异常；

### 参考代码

```python case2_数据校验.py
# ---------- 第 09 章 异常处理 · 案例 9-2：用 raise 与 assert 做数据校验 ----------
# 对应知识点：9.4 raise 主动抛出与 assert 断言、9.3 except ... as e、9.2 finally
# 功能说明：对车牌与车速做合法性校验，不合法时主动抛出异常，由统一入口捕获并给出提示

def check_plate(plate):
    """车牌校验：长度 7 位、第 2 位大写字母"""
    assert len(plate) == 7, "车牌长度必须为 7 位，当前 " + str(len(plate)) + " 位"
    if not plate[1].isupper():
        raise ValueError("车牌第 2 位必须为大写字母：" + plate)
    return True


def check_speed(speed):
    """车速校验：0~300"""
    assert isinstance(speed, (int, float)), "车速必须是数字"
    if speed < 0 or speed > 300:
        raise ValueError("车速超出合理范围 0~300：" + str(speed))
    return True


def verify(plate, speed):
    try:
        check_plate(plate)
        check_speed(speed)
    except AssertionError as e:
        print("[断言失败]", e)
        return False
    except ValueError as e:
        print("[数据非法]", e)
        return False
    else:
        print("[校验通过]", plate, speed, "km/h")
        return True
    finally:
        print("   —— 校验流程结束 ——")


verify("京A12345", 62)
verify("京A123", 62)
verify("京a12345", 62)
verify("京A12345", 320)
verify("京B67890", "快")
```

```text
   —— 校验流程结束 ——
[数据非法] 车牌第 2 位必须为大写字母：京a12345
   —— 校验流程结束 ——
[数据非法] 车速超出合理范围 0~300：320
   —— 校验流程结束 ——
[断言失败] 车速必须是数字
   —— 校验流程结束 ——
```

### 代码解读

| 代码段 | 对应知识点 | 作用 |

| `assert len(plate) == 7, "…"` | 9.4 | 断言失败抛 `AssertionError`，提示语带实际长度 |

# 第四部分　习题答案

## 答案 9-1　日志行解析的多异常捕获

> 对应 **练习 9-1**（第三部分）

### 参考代码

```python practice1_日志解析容错.py
# ---------- 第 09 章 异常处理 · 练习 9-1 参考答案：日志行解析的多异常捕获 ----------
# 对应知识点：9.2 try / except / else、9.3 except ... as e 与多异常、9.5 容错跳过
# 功能说明：解析日志行；字段不足抛 IndexError、车速非数字抛 ValueError，均返回空值继续处理

def parse_line(line):
    """返回 (车牌, 车速)，解析失败返回 (None, None)"""
    try:
        parts = line.split("|")
        plate = parts[1]              # 字段不足时抛 IndexError
        speed = int(parts[2])         # 非数字时抛 ValueError
    except IndexError:
        print("  [错误] 字段数不足：", line)
        return None, None
    except ValueError:
        print("  [错误] 车速不是整数：", line)
        return None, None
    else:
        return plate, speed


logs = [
    "08:15:32|京A12345|62",
    "08:16:02|京B67890",              # 缺字段
    "08:16:32|津C24680|快",           # 车速非数字
    "08:17:02|冀D11223|78",
    "08:17:32|京E55667|150",
]

ok = 0
fail = 0
for line in logs:
    plate, speed = parse_line(line)
    if plate is None:
        fail += 1
    else:
        ok += 1
        print("  解析成功：", plate, speed, "km/h")
    print("-" * 30)

print("成功", ok, "条，失败", fail, "条")
```

### 运行结果

```text
  解析成功： 京A12345 62 km/h
------------------------------
  [错误] 字段数不足： 08:16:02|京B67890
------------------------------
  [错误] 车速不是整数： 08:16:32|津C24680|快
------------------------------
  解析成功： 冀D11223 78 km/h
------------------------------
  解析成功： 京E55667 150 km/h
------------------------------
成功 3 条，失败 2 条
```

### 解析

1. **`try` 的范围**：只包住"切分 + 取字段 + 转换"三步，这正是可能出错的全部动作；`print` 与返回值放在 `else` 或 `except`，职责清晰。
2. **两种异常的分工**：`parts[1]`、`parts[2]` 越界抛 `IndexError`；`int("快")` 抛 `ValueError`。因此两条 `except` 顺序无所谓（类型不重叠），但都必须在 `Exception` 之前。
3. **用返回值而非异常判断成败**：调用方检查 `plate is None`，避免自己再包一层 `try`。这是"内层消化异常、外层只看结果"的分层设计。
4. **分隔线放在循环末尾**：无论成功失败都输出，保证 5 条样例各有 30 个短横线分隔，便于人工核对。

### 常见错误

| 错误现象 | 原因 | 修正 |
|---|---|---|
| 程序在第 2 条中断 | `try` 包在循环外 | 移入循环内 |
| 把 `IndexError` 写成 `ValueError` | 两者混用 | 列表越界是 `IndexError` |
| 失败计数为 0 | 用 `except: pass` 未计数 | 在 `except` 中累加 |
| 返回 `(None, None)` 后仍参与统计 | 缺少 `is None` 判断 | 调用方加判断 |

### 评分要点（供批改）

| 项 | 分值 | 观察点 |
|---|---|---|
| 两种异常捕获 | 4 | `IndexError` 与 `ValueError` 各自命中 |
| 提示信息 | 2 | 含出错行内容 |
| 返回值约定 | 2 | 失败返回 `(None, None)` |
| 统计与分隔 | 2 | 3 成功 / 2 失败，5 条分隔线 |

## 答案 9-2　批量录入中的异常跳过

> 对应 **练习 9-2**（第三部分）

### 参考代码

```python practice2_批量录入.py
# ---------- 第 09 章 异常处理 · 练习 9-2 参考答案：批量录入中的异常跳过 ----------
# 对应知识点：9.4 raise 主动抛出、9.5 用 continue 跳过坏数据、9.2 多异常捕获
# 功能说明：批量校验 6 条车速数据，非数字或超范围的记录跳过，汇总有效数据与平均值

raw = ["62", "abc", "-5", "118", "999", "78"]

valid = []
total = 0

for item in raw:
    try:
        speed = int(item)
        if speed < 0:
            raise ValueError("车速不能为负数")
        if speed > 300:
            raise ValueError("车速超过 300，疑似单位错误")
    except ValueError as e:
        print("[跳过]", item, "->", e)
        continue
    valid.append(speed)
    total += speed

print("有效数据：", valid)
print("有效条数：", len(valid), "| 无效条数：", len(raw) - len(valid))
if len(valid) > 0:
    print("有效平均车速：", round(total / len(valid), 1), "km/h")
else:
    print("无有效数据，无法计算平均值")
```

### 运行结果

```text
[跳过] abc -> invalid literal for int() with base 10: 'abc'
[跳过] -5 -> 车速不能为负数
[跳过] 999 -> 车速超过 300，疑似单位错误
有效数据： [62, 118, 78]
有效条数： 3 | 无效条数： 3
有效平均车速： 86.0 km/h
```

### 解析

1. **一个 `except` 覆盖三种原因**：非数字由 `int()` 抛、负数与超限由 `raise` 抛，类型都是 `ValueError`，因此只需一条 `except`，靠 `e` 的文本区分原因。
2. **`continue` 的作用**：跳过 `valid.append` 与 `total += speed` 两句，保证坏数据不污染统计。去掉 `continue` 后果很具体：`-5` 与 `999` 会被追加进 `valid`；`abc` 那轮 `int()` 在赋值前就抛出，`speed` 仍保留上一轮的 62，于是 62 被重复统计一次——这比"报错"更隐蔽。
3. **`raise` 的提示语设计**："车速超过 300，疑似单位错误"比"数据非法"更有诊断价值——它提示了可能的根因（单位写错）。
4. **零有效数据的兜底**：`if len(valid) > 0` 判断后计算平均值，避免 `ZeroDivisionError`，这是本知识点"先判断再计算"的通用写法。

### 常见错误

| 错误现象 | 原因 | 修正 |
|---|---|---|
| `-5` 被当作有效 | 未做负数判断 | `if speed < 0: raise` |
| `NameError: speed` | `continue` 缺失或位置错误 | `except` 末尾 `continue` |
| 分母为 0 报错 | 未判有效条数 | `if len(valid) > 0` |
| 提示语全是"数据非法" | 三种原因共用一句话 | 分别写清原因 |

### 评分要点（供批改）

| 项 | 分值 | 观察点 |
|---|---|---|
| 三条非法均跳过 | 4 | 原因提示各不相同 |
| `continue` 使用 | 2 | 坏数据不进入统计 |
| 统计结果 | 2 | 3 条有效、均值 86.0 |
| 兜底处理 | 2 | 零有效数据不崩溃 |

## 本章小结

- **六类异常**：`ValueError`、`TypeError`、`ZeroDivisionError`、`FileNotFoundError`、`IndexError`、`KeyError`，能按场景说出触发条件。
- **四子句**：`try` 监控、`except` 处理、`else` 无异常时执行、`finally` 始终执行；`except` 顺序从具体到宽泛。
- **主动抛出**：`raise ValueError("可定位的提示")` 用于业务规则；`assert` 用于内部不变量，`-O` 模式下失效。
- **容错骨架**：循环在外、`try` 在内、`except` 中 `continue`；两个计数器统计成败。
- **分层设计**：内层函数"发现问题"（抛/返回 `False`），外层调用方"决定处置"。
